# Phase 3 security review

Date: 2026-11-10. Scope: `main` at 8296c7d after the Phase 3 merges (card QR codes, staff sign-in and invitations, staff scan, points ledger with lots, expiry and reconciliation, member points history, staff LIFF app). Reviewer: the read-only `security-reviewer` agent; every finding verified by reading the code path end to end. Nothing from the Phase 1 or Phase 2 reviews regressed. Fixes are in migration `00007_hardening.sql`, the services named below, and the staff app; each has a test that failed before the fix.

## Deliberate choices

- F1: a 401 keeps the write pending, because the request may have been applied before the session ran out. The pending write lives in memory only (the body carries a scan token) and is shown only to the staff member who made it. Closing the LIFF app drops it; the banner text tells the cashier to check the member's history before discarding.
- F3: the fix requires a separate staff channel rather than adding a nonce to the member flow. Existing pilot apps must add the channel before staff can sign in again; the 409 and the dashboard help say how.
- F4: the platform ceiling silently caps spend-based earns (a large purchase earns the ceiling) but refuses a fixed-points earn above the cap, so a cashier sees the refusal. Admin adjustments keep their own 1,000,000-point limit.
- F4: the staff write limiter is in memory per API process. That is exact for the single-VM deployment; `StaffWritesPerMinute` below zero turns it off for tests only.
- F6: expiry runs inside writes. Reads still show the stored balance until the next write or the nightly job, which can briefly overstate a balance on screen but never lets expired points be spent.
- F11: invite codes issued before this change no longer match and must be re-issued from the dashboard. A fixed development key applies only when `SetInviteKey` is not called, which `cmd/api` always does.

## Accepted for now, with a plan

| Finding                                                                                                    | Plan                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| River's tables are reached through the application role, so a SQL injection in the API could enqueue jobs. | Phase 4: a separate `miniloyal_worker` role owns the River schema; the API role gets only `INSERT` on the job table through River's client. |
| Channel token cache is keyed by channel ID only (carried from Phase 2).                                    | Phase 5 (push messaging): key by channel ID plus a hash of the secret, and call `Forget` when a secret changes.                             |
| The staff write limiter is per process.                                                                    | Move it to Postgres or the shared limiter when the API runs more than one instance.                                                         |

## Confirmed clean

Card codes MAC'd under per-member keys derived with HKDF and compared in constant time; scan tokens bound to staff, member, app and tenant; every points write takes the account lock, consumes lots FIFO and keeps the ledger append-only; idempotency authorizes before claiming and before replaying; new tables under forced RLS with the standard policy; staff sessions in memory in the staff app with one re-exchange on 401; the staff app never puts tokens or scan tokens in browser storage.
