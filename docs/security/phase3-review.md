## Follow-ups from the Phase 3 test pass

- The staff keypad accepted nine digits for every field and truncated pasted text. It now refuses, as a whole, any amount above the API maxima (spend 100,000,000, points 1,000,000) and says so; `keypad-edges.test.tsx` runs the formerly skipped case.
- The staff app's error mapping listed codes the server never sends. It now follows the server: `scan_invalid` and `scan_mismatch` ask for a new scan, `scan_used`, `self_service`, `points_disabled` and `staff_channel_required` have their own messages, and any other 403 is a role refusal.
- The test pass's FINDING tests for F5, F6 and F13 now run and fail on a regression instead of skipping. Tests that documented the old behaviour (a retry after scan expiry refused with 403, a scan token surviving card rotation, fixed points up to 1,000,000 under any rule cap) now assert the fixed behaviour.

## Deliberate choices

- F1: a 401 keeps the write pending, because the request may have been applied before the session ran out. The pending write lives in memory only (the body carries a scan token) and is shown only to the staff member who made it. Closing the LIFF app drops it; the banner text tells the cashier to check the member's history before discarding.
- F3: the fix requires a separate staff channel rather than adding a nonce to the member flow. Existing pilot apps must add the channel before staff can sign in again; the 409 and the dashboard help say how.
- F4: the platform ceiling silently caps spend-based earns (a large purchase earns the ceiling) but refuses a fixed-points earn above the cap, so a cashier sees the refusal. Admin adjustments keep their own 1,000,000-point limit.
- F4: the staff write limiter is in memory per API process. That is exact for the single-VM deployment; `StaffWritesPerMinute` below zero turns it off for tests only.
- F6: expiry rows are written by writes and the job only; a refused write rolls its expiry back with it. Reads compute the spendable balance instead of writing, so a GET never changes the ledger.
- F11: invite codes issued before this change no longer match and must be re-issued from the dashboard. A fixed development key applies only when `SetInviteKey` is not called, which `cmd/api` always does.

## Fixed in Phase 4

- River's tables were reached through the application role, so a SQL injection in the API could enqueue, rewrite or delete jobs. Migration `00009_worker_role.sql` adds the `miniloyal_worker` login role. It owns River's tables, types and functions, and `cmd/worker` connects as it through `WORKER_DATABASE_URL`. `miniloyal_app` has nothing on River any more.
- `miniloyal_api` keeps what River's insert-only client needs and no more: `SELECT` and `INSERT` on `river_job`, `UPDATE` of the `kind` column only, and the `river_job_id_seq` sequence. `SELECT` is there because River's insert returns the row. The `kind` grant is there because River's unique insert ends in `ON CONFLICT DO UPDATE SET kind = river_job.kind`. A trigger refuses any update by a non-worker role that changes a row, so that grant cannot rewrite a job. The API role has nothing on `river_leader`, `river_queue`, `river_migration` or `river_notification`.
- Enqueueing stays possible from the API by design, since the API will enqueue jobs. Job arguments carry IDs only (F14), and each job loads its data inside a tenant or system transaction.
- The worker role is `NOBYPASSRLS` and a member of `miniloyal_app`. Points expiry, reconciliation and maintenance already run their cross-tenant work in system mode (`db.WithSystem`), so they need no bypass. The worker refuses to start as any role that is not `miniloyal_worker`, or as a superuser or `BYPASSRLS` role.
- `migrate up` reapplies the ownership and grants after every River migration, so tables added by a River upgrade are covered too. Tests: `TestAPIRoleCanOnlyInsertRiverJobs`, `TestWorkerRoleOwnsRiverOnly`, `TestRiverSchemaBelongsToTheWorker`, and the points expiry and maintenance jobs run end to end as the worker role (`TestPointsExpiryJobRunsOnceAsTheWorkerRole`, `TestMaintenanceRunsThroughRiver`).

## Confirmed clean

Card codes MAC'd under per-member keys derived with HKDF and compared in constant time; scan tokens bound to staff, member, app and tenant; every points write takes the account lock, consumes lots FIFO and keeps the ledger append-only; idempotency authorizes before claiming and before replaying; new tables under forced RLS with the standard policy; staff sessions in memory in the staff app with one re-exchange on 401; the staff app never puts tokens or scan tokens in browser storage.
